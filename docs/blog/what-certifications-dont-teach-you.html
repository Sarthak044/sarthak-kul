What Certifications Don't Teach You About Running Kubernetes in Production

August 27, 2026 · 6 min read · Sarthak Kulshrestha · Technical

  • Kubernetes
  • Career

CKA and CKAD are worth earning. They force you to actually know the API surface — how scheduling works, what a NetworkPolicy does versus what people assume it does, how to debug a pod that won't start under real time pressure. None of that is wasted knowledge. But there's a gap between passing a certification exam and running Kubernetes in production that nobody's syllabus quite covers, and it's worth naming honestly.

Multi-tenancy is where the clean mental model breaks first

Exam scenarios are almost always single-tenant: one cluster, one workload, one clear objective. Production clusters are usually shared — multiple teams, wildly different resource profiles, someone's batch job competing with someone else's latency-sensitive service. Understanding requests and limits conceptually is exam material. Tuning them across a shared cluster so that a spiky batch workload doesn't starve a customer-facing service is a different skill entirely, and it's mostly learned by getting it wrong once.

The first outage is (almost) never a control-plane bug

New Kubernetes operators tend to expect their first serious incident to be something exotic — an etcd quorum issue, a scheduler bug, something worthy of the complexity of the system. In practice, the first real outage is usually mundane: a memory limit set too conservatively, a liveness probe that's too aggressive, a PVC that quietly filled up. The certifications teach you the vocabulary to describe these problems. They don't teach you the instinct to suspect them first, before reaching for anything more exotic.

On-call reality versus calm study

Reading a Grafana dashboard while studying and reading the same dashboard at 3am with a director asking for an ETA are not the same cognitive task. Production competence includes a layer that has nothing to do with Kubernetes internals: staying calm enough to read a dashboard correctly under pressure, knowing which three signals actually matter when everything is red, and resisting the urge to change five things at once. That's trained by experience, not by an exam environment with a two-hour timer and a clearly scoped problem.

Institutional knowledge doesn't show up in the docs

Every production cluster accumulates a layer of tribal knowledge: why a particular namespace has a weird annotation, why nobody touches that one Helm chart without pinging a specific person first, which runbook is actually current versus which one is aspirational. None of this is written down anywhere a certification could test it, and a surprising amount of "senior" competence is just having absorbed enough of this institutional context to know where the bodies are buried.

Certifications are a floor, not a ceiling

None of this is an argument against certifying — CKA, CKAD, and similar credentials are a legitimate, efficient way to prove baseline fluency, especially early in a career or when moving into a new organization. The mistake is treating the certificate as evidence that the learning is finished. It's evidence that you're ready to start learning the parts that only running real systems, under real constraints, for real people, can teach you.

Closing thought

Keep certifying if it helps you learn — it's a good forcing function. Just keep the expectation calibrated: the exam proves you can operate the machine. Production teaches you to operate it responsibly, under pressure, with other people's uptime depending on your judgment. Those are related skills, but they're not the same skill.
