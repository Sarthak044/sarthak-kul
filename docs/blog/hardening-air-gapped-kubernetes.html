A Practical Checklist for Hardening Air-Gapped Kubernetes

July 18, 2026 · 6 min read · Sarthak Kulshrestha · Technical

  • Kubernetes
  • Security

Air-gapped clusters have a reputation for being the "safe" ones. No route to the public internet, no exposure to opportunistic scanning, no exfiltration path — what's left to worry about? In practice, quite a lot. Air-gapping removes one class of risk and quietly introduces a few others: stale images, unpatched CVEs sitting for months because nobody's pipeline reaches them, and a false sense of security that makes teams skip controls they'd never skip on a public cloud cluster.

This is the checklist I actually use when standing up or auditing a cluster with no direct internet route. It's not exhaustive, but it covers the places I've seen air-gapped environments quietly drift out of compliance.

1. Treat the image supply chain as the perimeter

With no ingress from the internet, your container images become the primary way anything new enters the environment. Mirror upstream registries into an internal registry (Nexus and JFrog both work well here), and scan every image with Trivy before it gets mirrored — not after. Once an image is inside an air-gapped registry, it tends to stay trusted by default, so the scanning gate has to sit at the border, not somewhere convenient downstream.

Sign images on the way in if you can. It's a small extra step that pays for itself the first time someone asks "how do we know this image wasn't tampered with between the vendor and our registry?"

2. Default-deny network policy, even without an internet path

It's tempting to relax NetworkPolicy rules in an air-gapped cluster on the logic that there's "nowhere for traffic to go anyway." That logic breaks the moment a workload is compromised and starts moving laterally between namespaces instead of outward. Default-deny egress and explicit allow-lists are just as relevant inside a sealed network as outside one:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress: []

Layer HA ingress (Traefik or Kong Gateway OSS both handle this well) on top so that legitimate traffic still has a clear, auditable path in and out of each namespace.

3. Harden the node OS and the container runtime, not just the app

CIS benchmarks exist for a reason, and air-gapped nodes are not exempt from them. Non-root execution, read-only root filesystems, and a minimized base image cut down the blast radius of anything that does get through. This is also where multistage Docker builds earn their keep — ship the compiled artifact, not the toolchain that built it.

4. Plan your patch cadence before you need it

Without live internet access, patching is a scheduled event, not a background process. Mirror upstream patch repositories on a fixed cadence, build golden images against them, and roll nodes rather than patching in place. The teams that struggle here are the ones that treat air-gapped patching as an exception process instead of a routine one — by the time a CVE is urgent, you want the mirror-and-rebuild pipeline to already be boring.

5. Observability has to be self-hosted too

Every SaaS observability agent you can't use is one more reason to invest properly in the self-hosted stack: Prometheus for metrics, Grafana for dashboards, Loki for logs, Tempo for traces. None of it should quietly try to phone home — audit outbound configuration on these tools specifically, since many ship with telemetry defaults aimed at a connected world.

Closing thought

Air-gapping changes your threat model — it doesn't retire it. The checklist above isn't about distrust of the environment; it's about not letting the absence of one risk (external exposure) quietly excuse the rest (supply chain integrity, lateral movement, patch debt, blind observability). Treat "air-gapped" as a constraint to design around, not a control you get for free.
